Why not just one signal

Meaning and wording disagree more than you'd expect

Dense embeddings are excellent at "what does this mean" — they'll surface a test about redirect loops even if you ask about "infinite bounce-back," because they compare meaning, not characters. They're bad at exact tokens: ask for VWO-2481 and a purely dense search may hand back five plausible-looking neighbors that are all the wrong ticket. Sparse embeddings are the mirror image — exact on tokens and IDs, blind to paraphrase. bge-m3 produces both from a single forward pass, so neither signal costs a second model.

Dense · semantic

Continuous, 1024 dimensions. Finds paraphrase and intent. Loses exact identifiers.

Sparse · lexical

Discrete token weights. Finds exact wording and IDs. Loses paraphrase and intent.

Five techniques, one pipeline

What each stage is actually doing

Each of these is a real, independently swappable piece — none of them assume the others exist.

01

Hybrid embeddings

One BGEM3FlagModel.encode() call returns a 1024-dim dense vector and a sparse lexical-weight map for every chunk — no second model to keep in sync, no separate BM25 index to maintain.

bge-m3
02

Storage & fusion

Qdrant holds both vector types on the same point and fuses them with a native RRF query — prefetch a dense list and a sparse list, ask for Fusion.RRF, get one ranked list back. Runs identically against the embedded on-disk store this demo ships with, or a full Qdrant server.

Qdrant
03

Cross-encoder reranking

Vector similarity is fast but approximate. The top candidates get a second look from a cross-encoder that reads the query and each chunk together — only the strongest 4 survive to the prompt.

04

Query rewriting

Before retrieval, the question is rewritten into three alternate phrasings and searched alongside the original. Recall goes up because the corpus rarely uses the same words the user does.

Openrouter
05

Grounded generation

Surviving chunks go to the model with instructions to cite [Chunk N] and to say plainly when the corpus doesn't answer the question. A phrasing heuristic ("create a test case for...") switches modes and drafts a new, structured test case from the retrieved examples instead.

Openrouter · deepseek

How this got built

Vibe-coded, then verified

The dataset came first: a seeded Python generator crosses 20 VWO modules against 11 test types and a bank of browser/device variants, so re-running it produces the identical 5,000 rows every time. Then the retrieval stack — bge-m3 for hybrid embeddings, Qdrant in embedded mode so nobody needs Docker for a demo, bge-reranker-v2-m3 for the second pass, Openrouter for rewriting and generation.

Before any of it got wired into the Flask app, the exact Qdrant calls it depends on — dense search, sparse search, native RRF fusion, payload filtering, faceted filters — were run against the actual installed client library in a throwaway collection first. Then the full ingest-to-chat path was run end to end with the model calls swapped for deterministic fakes, to prove the data — chunk counts, point IDs, citation numbering, the highlight state that connects a chat answer back to the chunk browser — actually flows through correctly. Nothing on this page is a diagram of what the code is supposed to do; it's a diagram of what was run.
